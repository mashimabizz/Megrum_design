# 26. Trust & Safety / 審査前運用SOP

最終更新: 2026-06-29
ステータス: Draft（初回提出前の運用手順、評価・通報・ブロック・モデレーション / 削除申出・送信防止措置 / 退会申請・削除予定 / 顔候補付け / Sensitive Info論点を追加）

## 目的

App Store審査で確認されやすいUGC、通報、ブロック、モデレーション、アカウント削除、個人情報請求、AI機能の安全運用を、初回リリース前に説明可能な状態へそろえる。
個人情報・セキュリティ事故の初動、証跡保全、PPC報告準備、本人通知は `notes/49_privacy_security_incident_response_runbook.md` を使う。
この文書は運用手順であり、コードやDBを変更しない。

## 1. 対象範囲

| 領域 | 対象 |
|---|---|
| UGC | プロフィール、グッズ画像、グルーム、スポット掲示板、取引チャット、証跡写真、評価 |
| 取引安全 | 打診、ネゴ、合意、現地交換、異議申し立て |
| 通報 | ユーザー通報、グッズ通報、掲示板通報、取引通報、問い合わせ経由の通報 |
| 削除申出 | 権利侵害、名誉毀損、プライバシー侵害、違法又は不適切な情報に関する削除申出、送信防止措置、発信者確認又は通知 |
| ブロック | ユーザー単位の表示制限、通知制限、返信制限 |
| アカウント | 削除申請、削除猶予、連携解除、復旧可否 |
| プライバシー | 開示等請求、第三者提供記録、漏えい疑い |
| AI | AI入力、AI出力、顔候補付け、外部AI送信、学習利用、誤判定 |

## 2. 受付チャネル

| チャネル | 用途 | 初回提出前の確認 |
|---|---|---|
| アプリ内通報 | UGC、ユーザー、取引、グッズの問題 | 対象画面ごとに動作確認。直接ボタンがない対象はsupport@へのフォールバックを明示 |
| アプリ内問い合わせ | ログイン中ユーザーのサポート | 送信先と受付確認 |
| `support@megrum.jp` | ログイン不能、法務、削除、プライバシー請求 | 受信確認 |
| App Store Review Notes | Apple審査員への説明 | デモアカウントとレビュー経路を記載 |

受付番号の形式候補:
- 通報: `REP-YYYYMMDD-0001`
- 異議申し立て: `DPT-YYYYMMDD-0001`
- 個人情報請求: `PRV-YYYYMMDD-0001`
- アカウント削除: `DEL-YYYYMMDD-0001`

## 3. 優先度

| 優先度 | 内容 | 初動 |
|---|---|---|
| P0 Critical | 身体的危険、脅迫、未成年の危険、個人情報の露出、詐欺、盗品疑い、チケット転売、決済事故、漏えい疑い | 速やかに確認。必要なら対象非表示、取引停止、アカウント制限 |
| P1 High | 嫌がらせ、なりすまし、権利侵害、無断の顔写真/顔特徴量利用、虚偽評価、報復通報、スパム大量投稿、取引不履行、重大なAI誤判定 | 優先確認。必要なら一時制限 |
| P2 Normal | 軽微な不適切投稿、表記ゆれ、単発の不具合、使い方質問 | 通常サポート |
| P3 Low | 要望、UI改善、情報提供のみ | 次回改善へ記録 |

## 4. 通報対応フロー

1. 通報を受け付ける。
2. 対象、通報理由、通報者、対象ユーザー、関連取引又は投稿を確認する。
3. P0/P1/P2/P3 を仮判定する。
4. P0又はP1の場合、必要に応じて対象コンテンツを一時非表示、取引を一時停止、相手への通知を制限する。
5. 取引チャット、証跡、投稿、画像、ログ、過去通報を確認する。
6. 措置を決定する。
7. 通報者へ受付又は完了を通知する。
8. 対象ユーザーへ、必要な範囲で警告、制限、削除理由を通知する。
9. 対応内容、根拠、担当者、日時を記録する。

注意:
- 通報者の情報は原則として対象ユーザーへ直接伝えない。ただし、申告内容、証跡、取引状況から推測され得ること、法令対応・公的機関・アプリストア・外部サービスへの報告では必要な範囲で開示し得ることをFAQ/Privacyと揃える。
- 通報は緊急通報の代替ではない。身体の危険、犯罪被害、差し迫った脅迫、ストーカー行為は警察、消防、医療機関、会場スタッフ、施設管理者等への連絡を案内する。
- 虚偽、誇張、報復、嫌がらせ、不当要求目的の通報は、通報者側の制限候補として記録する。

措置候補:
- 何もしない
- 注意喚起
- 投稿又は画像の削除
- 投稿又は画像の非表示
- 取引一時停止
- 機能制限
- 一時停止
- 永久停止
- 法令対応又は関係機関相談

## 4.1 権利侵害・削除申出対応

権利侵害、名誉毀損、プライバシー侵害その他違法又は不適切な情報に関する削除申出は、通常の通報とは分けて記録する。

受付時に確認する情報:
- 申出者の連絡先、本人又は権利者/代理人であることの確認に必要な情報
- 対象コンテンツのURL、画面名、投稿ID、取引ID、スクリーンショット
- 侵害されている権利又は問題の内容
- 削除、非表示、送信防止措置、発信者確認又はその他希望する対応
- 緊急性、身体的危険、個人情報露出、未成年者への影響

対応方針:
- 法令、ガイドライン、利用規約、プライバシーポリシー、内部基準に基づき、削除、非表示、表示範囲制限、アカウント制限、何もしない、追加確認、関係機関相談を判断する。
- 発信者への確認又は通知が必要な場合、申出者の安全、通報者秘匿の限界、対象者の反論機会、証跡保全を分けて記録する。
- 法令上必要な場合を除き、全件の削除、一定期間内の回答、発信者情報開示、個別理由の詳細開示を約束しない。
- 情報流通プラットフォーム対処法上の大規模特定電気通信役務提供者として指定された、又は指定可能性が出た場合は、申出窓口、削除基準、通知、運用状況の公表、担当体制を別途見直す。

公開前No-Go:
- [ ] 公開ページやFAQで「7日以内に必ず削除/回答」「申出どおり必ず削除」「発信者情報を必ず開示」「Megrumは常時監視している」と書いていない。
- [ ] 削除申出窓口を公開する場合、受付情報、本人/権利者確認、対象特定、記録保存、発信者確認又は通知のテンプレートがある。
- [ ] 大規模指定事業者向け義務を自ら適用対象として断定していない。該当可能性が出た場合の再確認先を `notes/17_legal_alignment.md` に残している。

## 5. UGC審査前チェック

AppleのUGC審査観点に合わせ、提出前に次を確認する。

- [ ] 不適切なコンテンツ投稿を抑止するルール又はフィルタがある
- [ ] 不適切なコンテンツを通報できる
- [ ] 通報へ適時対応する運用がある
- [ ] 迷惑ユーザーをブロックできる
- [ ] 公開問い合わせ先がある
- [ ] 投稿、画像、返信、プロフィール、取引チャットそれぞれの通報入口が説明できる
- [ ] 掲示板を出す場合、Swift Native画面からスレッド/返信通報へ到達できる。現行検索ではDB RPCはあるがSwift呼び出し導線は未確認のため、未実装ならsupport@フォールバックをReview Notes/FAQへ明記する
- [ ] 評価コメントが公開される場合、誹謗中傷、個人情報、虚偽評価への禁止と削除/非表示裁量を説明している
- [ ] 緊急時はアプリ内通報だけを待たない案内がある
- [ ] 未完成のUGC機能を初回提出ビルドで露出していない

審査メモには、UGC領域、通報、ブロック、モデレーション体制を短く明記する。

## 6. ブロック対応

ブロック後の期待挙動:
- ブロックした相手のグルーム、掲示板スレッド、返信、通知を表示しない。
- ブロック関係にある相手からの返信通知、メンション通知を作成しない。
- 検索結果、ホーム候補、公開プロフィール、評価一覧など交換候補面からブロック相手を外せる範囲を確認する。
- 進行中又は過去の取引がある場合、安全確保と紛争対応のため、必要な取引情報、取引チャット、証跡、評価、通報記録は保持する。
- ブロックだけで危険が解消しない場合、通報又は問い合わせへ誘導する。

提出前に、ブロック画面、解除画面、ブロック後の表示制限を実機で確認する。

## 7. アカウント削除SOP

詳細な削除対象、保持対象、サポート文面、Sign in with Apple token revoke確認は `notes/45_account_deletion_privacy_request_runbook.md` を使う。

1. ユーザーがアプリ内設定からアカウント削除を開始する。
2. 削除対象、保存が続く情報、サブスクリプション解約、削除予定日の意味、復旧/取消が保証されないことを確認画面又は公開ページで説明する。
3. ユーザーが明示的に削除を確認する。
4. 削除申請を記録し、アカウントを削除予定状態にする。
5. 進行中の取引、異議申し立て、未払い、法令対応があれば処理を保留又は制限する。
6. Apple / Googleログイン連携がある場合、必要に応じてトークン失効又は連携解除を行う。
7. 削除予定日以降の実削除、匿名化、Auth削除/無効化、Storage削除、APNs token無効化、Apple/Google連携解除の手順を決める。
8. 法令遵守、不正利用防止、紛争対応、会計、監査のために保存する情報を分離管理する。
9. 削除完了通知、手動処理記録又は問い合わせ回答の運用を決める。

提出前チェック:
- [ ] アプリ内から削除を開始できる
- [ ] サポート窓口だけに依存していない
- [ ] 削除対象と保持対象を説明している
- [ ] サブスクリプション解約はApp Store側で必要と説明している
- [ ] Appleログイン利用時のトークン失効方針がある
- [ ] 30日後の実削除ジョブ、申請取消/復旧、APNs token無効化、削除完了通知が未確認のまま公開文面で保証されていない

## 8. 個人情報請求SOP

詳細な受付、本人確認、回答テンプレート、対応履歴は `notes/45_account_deletion_privacy_request_runbook.md` を使う。

対象:
- 利用目的の通知
- 開示
- 訂正、追加、削除
- 利用停止、消去
- 第三者提供停止
- 第三者提供記録の開示

対応フロー:
1. `support@megrum.jp` 又はアプリ内問い合わせで受付。
2. 受付番号を発行。
3. 本人確認を行う。
4. 請求対象の情報を特定する。
5. 法令上対応できる範囲を確認する。
6. 必要な手数料があれば事前案内する。
7. 回答、訂正、削除、利用停止等を実施する。
8. 対応履歴を記録する。

開示に注意が必要な情報:
- 他ユーザーの個人情報
- 通報者の安全に関わる情報
- 不正利用検知やセキュリティに関わる内部情報
- 取引相手との紛争対応中の証跡
- 法令上保存が必要な情報

## 9. AI機能SOP

初回提出でAI機能を出す場合、次の分類を必ず記録する。

| 分類 | 例 | 必要対応 |
|---|---|---|
| オンデバイスAI | 端末内画像解析、切り出し補助 | 権限説明、出力確認導線 |
| 自社サーバーAI | 自社APIでの分類、検索補助 | プライバシーポリシー、ログ管理 |
| 外部AIサービス | 外部APIへ画像又は本文を送信 | 送信情報、目的、送信先、保存期間、学習利用の有無、同意 |
| モデレーションAI | 不適切投稿検知、通報補助 | 誤判定時の確認、異議申し立て導線 |
| 顔候補付け | グッズ画像からの顔/キャラクター検出、候補提示、補正履歴 | Face ID/本人確認ではない説明、Sensitive Info回答、同意記録、削除/保持、外部送信有無 |

AI出力事故時の対応:
1. 対象入力、出力、利用画面、影響範囲を確認する。
2. 誤登録、誤投稿、誤通報、個人情報送信の有無を確認する。
3. 必要なら該当機能を一時停止する。
4. ユーザーに修正方法又は削除方法を案内する。
5. 外部AIサービス利用時は、送信先のログ、保存期間、削除可否を確認する。
6. 顔候補付け事故時は、対象画像、顔検出結果、候補、補正履歴、特徴量、同意記録、外部送信の有無を確認し、必要に応じて削除、無効化、非表示又は機能停止を行う。
7. 再発防止策を記録する。

## 10. 取引不履行・個人情報トラブルSOP

現地交換前後の安全とプライバシー保護のため、次をP0として扱う。

- 合意済み条件と異なる受け渡しを強要する
- 相手から不要な個人情報又は外部連絡先を求められる
- 実名、電話番号、座席番号、顔写真などが公開投稿に載る
- 取引チャット外での連絡や合流を強要する
- 現地で危険な場所や時間帯への移動を求められる

対応方針:
- 公開投稿への不要な個人情報、座席番号、顔写真は削除又は非表示にする。
- 取引不履行や危険誘導は、取引チャット、証跡、双方の申告を確認する。
- 運営は取引当事者ではなく受け渡し結果を保証しないが、規約違反対応と安全措置は行う。

## 11. 審査提出時の証跡パック

提出前にスクリーンショット又は短い動画で残すもの:

- 通報入口
- ブロック入口
- 問い合わせ入口
- 利用規約 / プライバシー / 特商法ページ
- アカウント削除入口
- App Privacy回答と `PrivacyInfo.xcprivacy` の照合メモ
- AI機能を出す場合は同意又は説明画面
- 顔候補付けを出す場合は、Face ID/本人確認ではない説明、Sensitive Info回答、削除/同意/保持の確認証跡
- TestFlightで2アカウントの打診から取引完了まで通った記録

## 12. 審査週の運用ルーチン

毎日確認:
- P0通報
- ログイン不能問い合わせ
- アカウント削除問い合わせ
- 個人情報請求
- 課金問い合わせ
- App Store Connect のメッセージ
- TestFlightフィードバック

審査リジェクト時:
1. Appleの指摘文を保存する。
2. 該当ガイドライン番号を確認する。
3. 実装修正が必要か、メタデータ修正で足りるか分ける。
4. メタデータ修正で済む場合、審査メモ、スクショ、説明文を修正する。
5. 実装修正が必要な場合、別セッションの開発タスクへ切り出す。
6. 再提出時に、何を変更したかをApp Review Notesへ明記する。
