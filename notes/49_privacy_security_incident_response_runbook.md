# 49. 個人情報・セキュリティ事故初動ランブック

最終更新: 2026-06-29

ステータス: Draft v0.2（運用前・法務レビュー前、漏えい等初動・事故疑いの責任承認境界）

## 目的

Megrumで個人情報、アカウント、取引チャット、画像、位置情報、外部サービス、秘密情報に関わる事故又は事故疑いが起きた時に、初動、証跡保全、通知、報告、再発防止を迷わず進める。

この文書は運用手順であり、コード、DB、外部サービス設定は変更しない。

法令判断が必要な場合は、弁護士、個人情報保護委員会の公式情報、各外部サービスの契約条件を確認する。

提出前の予防監査は `notes/54_prelaunch_security_audit_checklist.md` を使い、RLS、Storage、secret、APNs、管理者権限のNo-Goを残さない。

## 1. 対象になる事象

| 分類 | 例 | 初動優先度 |
|---|---|---|
| 個人データ漏えい疑い | Supabase RLS設定ミス、Storage公開範囲ミス、問い合わせ誤送信、証跡画像の誤公開 | P0 |
| 不正アクセス疑い | 管理者アカウント侵害、API key流出、Supabase service role key流出、APNs秘密鍵流出 | P0 |
| アカウント事故 | 他人のプロフィール、在庫、wish、取引チャットが見える | P0 |
| 位置情報事故 | 現在地、待ち合わせ場所、スポット情報が意図しない相手に見える | P0 |
| 通知事故 | APNs通知本文が誤った相手に届く、通知に過剰な個人情報が入る | P0 |
| 外部サービス事故 | 外部AI、地図API、分析/クラッシュ、サポートツールへ想定外データを送る | P0/P1 |
| App Privacy不一致 | 実ビルドで収集しているデータがApp Store Connect回答やプライバシーポリシーとズレる | P1 |
| 軽微な運用ミス | 個人情報を含まない管理メモの誤記、内部台帳の記録漏れ | P2 |

## 2. 報告・通知が必要になりやすい条件

個人情報保護委員会の案内では、個人の権利利益を害するおそれがある一定の漏えい等について、報告と本人通知が必要になる。2026-06-29時点の公式案内を前提にするが、実際の期限、様式、報告先、判断基準は事案発覚時点の公式情報と弁護士確認に従う。

Megrumで特に注意する条件:

| 条件 | Megrumでの想定 |
|---|---|
| 要配慮個人情報が含まれる | ユーザーが自由記述、画像、通報、問い合わせに健康、信条、犯罪被害等を書いた |
| 財産的被害のおそれ | 決済情報、購入状態、ログイン情報、悪用可能な認証情報が関係する |
| 不正目的の行為によるもの | 不正アクセス、盗難、内部者持ち出し、ランサムウェア、改ざん |
| 対象本人が1,000人を超える | 設定ミスや一括処理で多数ユーザーの情報が露出した |

判断に迷う場合は、P0として扱い、弁護士確認に回す。

## 3. タイムライン

| 時間 | やること | 完了条件 |
|---|---|---|
| 発覚から15分以内 | 受付番号発行、Incident Lead仮決定、証跡保全開始 | `INC-YYYYMMDD-0001` を作る |
| 30分以内 | 影響範囲の仮判定、P0/P1/P2分類、拡大防止策を決める | 一時停止、非表示、key rotation等の候補を決定 |
| 60分以内 | オーナー、開発担当、法務担当、サポート担当へ共有 | 事実、未確認、次の確認を分けて共有 |
| 24時間以内 | 対象データ、対象人数、原因、再発防止の暫定メモを作る | 本人通知・PPC報告の要否を法務確認へ回す |
| 3〜5日以内目安 | 報告対象なら速報を準備 | 速報に必要な項目を埋める |
| 30日以内目安 | 確報を準備 | 原因、影響、措置、再発防止を更新 |
| 60日以内目安 | 不正目的のおそれがある場合の確報期限を意識 | 不正アクセス系の調査結果を反映 |

実際の期限、報告先、様式は事案発覚時点の公式情報で確認する。

## 4. 役割

| 役割 | 担当 | やること |
|---|---|---|
| Incident Lead | オーナー又は指定担当 | 優先度、停止判断、社外連絡判断 |
| Engineering | 開発担当 | ログ確認、原因調査、拡大防止、修正タスク化 |
| Privacy / Legal | 弁護士又は法務確認担当 | PPC報告、本人通知、公開文面、保存方針の判断 |
| Support | `support@megrum.jp` 担当 | 受付返信、本人通知、問い合わせ一次対応 |
| App Store Owner | App Store Connect担当 | App Privacy、Review Notes、公開URLの更新判断 |

少人数運用では兼務してよいが、Incident Leadと記録担当だけは必ず置く。

## 4.1 初動連絡・公表の法務トーン

初動連絡で言う:
- 事実として確認できていること。
- 未確認で調査中のこと。
- 被害拡大防止のために実施した措置。
- ユーザーにお願いしたい具体的な行動。
- 問い合わせ先と受付番号。

初動連絡で言わない:
- 影響範囲が未確定の段階で「漏えいはありません」と断定する。
- 原因が未確定の段階で、外部サービス、ユーザー、特定担当者、第三者の責任だと断定する。
- 法務確認前に、法的責任、賠償、補償、返金、相手会員への措置、復旧時刻、再発防止の完全性を約束する。
- 実パスワード、secret、token、本人確認書類、影響外ユーザー情報、内部ログ全文を本文又は添付に含める。
- App Store公開レビュー、SNS、公開FAQだけで個別事故対応を完了扱いにする。

使いやすい表現:
- `確認すべき事象を把握しました。`
- `現在、影響範囲と原因を確認しています。`
- `被害拡大防止のため、対象機能の一時制限等を行う場合があります。`
- `法令上必要な場合は、本人通知及び関係機関への報告を行います。`
- `追加でお知らせすべき事項が判明した場合は、改めてご連絡します。`

避ける表現:
- `漏えいしました`（法務確認前）
- `漏えいはありません`（影響範囲未確定）
- `当社の責任です`（責任判断前）
- `必ず補償します`
- `全て復旧済みです`（検証未完了）
- `二度と起きません`

## 5. 初動チェックリスト

### 5.1 事実の切り分け

- [ ] いつ発覚したか
- [ ] 誰から報告されたか
- [ ] どの環境か。本番、TestFlight、開発、管理画面、公開ページを分ける
- [ ] 対象データは何か。メール、プロフィール、在庫、wish、取引チャット、画像、位置情報、通知token、購入状態、問い合わせ、通報を分ける
- [ ] 対象人数は何人か。概算と根拠を分ける
- [ ] 外部サービスが関係するか。`notes/48` の台帳で照合する
- [ ] まだ継続中か、すでに止まっているか

### 5.2 拡大防止

- [ ] 公開バケット、RLS、管理画面、公開URL、API key、通知送信、外部AI送信を確認する
- [ ] 必要なら該当機能を一時停止する
- [ ] 漏れた可能性のあるkey、token、secretを無効化又は更新する
- [ ] 対象投稿、画像、通知、問い合わせ履歴を一時非表示又はアクセス制限する
- [ ] 証跡を消す前に、必要最小限のログとスクショを安全な場所へ保存する

### 5.3 証跡保全

証跡に含めるもの:
- 発覚日時、報告者、受付チャネル
- 画面、URL、API、テーブル、Storage bucket、Function名
- 影響データの種類、件数、対象期間
- 対応者、実施した措置、実施時刻
- 外部サービスへの問い合わせ履歴

証跡に含めないもの:
- 実パスワード
- 秘密鍵、service role key、API secret
- 不要な本人確認書類
- 影響外ユーザーの個人情報
- 公開してよいか未確認のスクショ

## 6. 判定表

| 判定 | 条件 | 対応 |
|---|---|---|
| P0 Reportable候補 | 報告・本人通知が必要になり得る条件に該当 | 法務確認、速報準備、本人通知案作成 |
| P0 Security | key流出、不正アクセス、他人データ閲覧、位置情報露出 | 即時拡大防止、key rotation、影響調査 |
| P1 Privacy Mismatch | App Privacy、プライバシーポリシー、実装の不一致 | App Store Connect回答、公開文面、実装範囲を修正判断 |
| P1 Vendor | 外部サービスへ想定外送信 | ベンダー問い合わせ、削除可否確認、法務確認 |
| P2 Ops | 外部影響のない内部記録ミス | 記録修正、再発防止メモ |

```
・該当画面

この受付は、事実確認及び被害拡大防止のための初動対応です。現時点で、漏えい等への該当性、原因、責任、補償、返金又は復旧を確定するものではありません。
```

## 9. PPC報告準備メモ

正式な報告は、最新の公式フォームと弁護士確認に従う。

事前に整理する項目:
- 報告者の名称
- 発覚日時
- 事故の概要
- 原因
- 対象となる個人データの項目
- 対象人数
- 二次被害のおそれ
- 本人通知の状況
- 公表の有無
- 再発防止策
- 委託先又は外部サービスの関与
- 速報か確報か

## 10. App Store / 公開文面の更新判断

事故又は事故疑いの内容によって、次も確認する。

| 対象 | 更新が必要なケース |
|---|---|
| App Store Connect App Privacy | 収集データ、利用目的、リンク有無、第三者SDKが変わった |
| プライバシーポリシー | 外部サービス、利用目的、保持期間、委託先、本人通知方法が変わった |
| サポートページ | 事故に関する問い合わせ導線を追加する |
| Review Notes | 審査中に安全/プライバシー措置を説明する必要がある |
| App Store Availability | 公開継続が危険で、地域Availability変更、Remove App From Sale、new build判断が必要 |
| `notes/27` | データインベントリを更新する必要がある |
| `notes/48` | 外部サービス/委託先の扱いが変わった |

AppleのApp Privacy回答は、実際のデータ取扱いと最新状態を一致させる。
公開停止又はAvailability変更が必要な場合は `notes/73_app_store_availability_emergency_stop_runbook.md` を使う。

## 11. No-Go

- 事故疑いを受けたのに、受付番号と初動記録を作らない。
- 秘密鍵や実パスワードを証跡に貼る。
- 影響範囲が未確認のまま「漏えいはありません」と断定する。
- 不正アクセス疑いがあるのにkey rotationやログ保全を後回しにする。
- 本人通知又はPPC報告が必要かもしれないのに法務確認に回さない。
- App Privacyと実装の不一致を認識したまま提出する。
- 初動連絡、本人通知、公開レビュー返信又はSNSで、法務確認前に責任、補償、返金、復旧、相手会員への措置、原因、再発防止の完全性を断定する。
- 公開レビュー、SNS、公開FAQに、事故の対象ユーザー、取引、通報、認証情報、証跡URL、内部ログ又は影響外ユーザー情報を書き込む。
