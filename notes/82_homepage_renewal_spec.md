### 0A-2. そのまま使える確定コピー（事実整合済み）

- 「譲・求のシェア画像が、すぐ作れる。」（§4-1）
- 「正確な現在地は表示されません。」（位置・めぐり言及時の必須併記）

- 「会って直接だから、住所を教える必要がない。送料ゼロ・実物を確認してから交換。」（現地）
- 用語：取引チャット／打診／郵送交換／マイグッズ／ほしいもの／個別募集／めぐり／グルーム／チャットルーム／めぐりあった人

### 0A-3. コピー方針（オーナー決定 2026-07-12 反映）

- **「お品書き」「30秒」**：決定＝**使わない**。主表記「譲・求のシェア画像」／訴求「すぐ作れる」で確定（§12-6/7）。
- **プレミアム/有料機能**：決定＝**初回から有料**（§12-9）。機能の事実説明は可。ただし**価格・購入導線の実表示はGo条件**（特商法ページ・ASC商品/価格・FAQ・Review Notes・サーバー検証：`notes/63` CM-008／`notes/17` L16）**充足後**。それまで購入ボタン・価格を出さない。
- **特商法ページ**：正式 `/legal/commerce` 公開までリンクしない。初回有料方針のため公開は必須（§12-8）。
- **分析**：決定＝**Vercel Analytics 採用**。Privacyへ解析利用を追記＋台帳記載後に有効化（§6-1）。

## 1. ホームページが果たすべき役割（優先順位つき）

### 役割1（最重要）：「怪しくないこと」の証明 — 信頼形成

- 新規アプリ、個人開発、位置情報を扱う、住所を扱う——ユーザーが必ず「Megrum 怪しい」「Megrum 安全」で検索する（`notes/78` §M1 で PR の受け皿としても明記済み）。
- その検索の着地点として、**運営の顔・安全の仕組み・お金の話（無料の範囲）・法務ページ**へ2クリック以内で到達できること。
- 判断材料：位置情報の扱い（「正確な現在地は表示されません」必須併記）、住所の扱い（成立後・送る相手だけ）、証跡・相互評価・通報の仕組み、未成年への配慮。
- 「出会い系ではないか」という懸念に対し、**語彙と設計の両方**で答える（異性想起ゼロ・グッズ交換に閉じた説明）。

### 役割2：X → LP → DL のコンバージョン

- 流入の主経路は公式X（フォロワー約500人〜）とUGC（譲求シェア画像の透かし・QR）。
- Xの140字で伝えきれない価値を、**スクロール1画面目で「譲・求のシェア画像がすぐ作れる」**、2画面目以降で交換マッチングの価値として伝える。
- CTAはフェーズで変わる（§6）。ローンチ前に「ダウンロード」ボタンを置かない（クリック先がない状態を作らない）。

### 役割3：安全ガイド・交換マナーの公式リファレンス

- `notes/78` M0 タスク「安全・法務の先出し：位置情報の扱い説明／未成年安全ガイド／現地交換マナーを megrum.jp に公開」の実装先。
- X安全Tips投稿（`notes/80` §4-2）の「詳しくはこちら」リンク先として機能し、**アプリ未DL層にも価値がある**コンテンツにする（=SEOとUGC拡散の資産）。

### 役割4：App Store 審査・PR・店舗打診の「公式らしさ」担保

- 審査のマーケティングURL・サポートURL、PR TIMES配信、鶴橋店舗QRの着地先。
- 記者・店舗オーナー・保護者が見ても「ちゃんとした運営」に見える情報密度と体裁。

### 役割5：SEO（中長期の無料流入）

- 狙うキーワード（競合空白・`notes/78` §M0 ASO と整合）：「グッズ交換 アプリ」「推し活 交換 アプリ」「トレカ 交換 アプリ」「現地交換」「譲 求 アプリ」＋安全系ロングテール（「グッズ交換 詐欺 対策」「グッズ交換 住所 教えたくない」）。
- 安全ガイド群と `/articles` の継続記事がロングテールを拾う設計。
- 記事は「安全・トラブル対策」「交換ノウハウ」「推し活・現場Tips」「Megrumの使い方」「お知らせ」の5分類とし、各記事から関連機能・安全ページ・App Store CTAへ内部リンクする。

### 役割6：公開後も育てられるコンテンツ基盤

- オーナーまたはAIがMarkdown/MDXを1ファイル追加するだけで、記事一覧・記事詳細・sitemap・関連記事が更新されること。
- v1ではブラウザ投稿CMSを作らない。Gitを介さず投稿したい運用要件が生まれた時点でmicroCMS等を別途比較する。
- noteは配信・再編集先として併用できるが、検索資産にしたい記事の正本は megrum.jp とし、重複掲載時は要約転載またはcanonical方針を決める。

### やらないこと（アンチスコープ）

- ブラウザから投稿する管理画面付きCMSの構築（v1はリポジトリ内Markdown/MDXで代替）
- 多言語対応（日本語のみ。英語は将来）
- Web版アプリ機能・Webからの会員登録（アプリに閉じる）
- 実在アーティスト・実在グッズの写真掲載（`notes/80` §1-3。スクショは架空グループのダミーデータ）
- 代表者氏名の公表（`notes/17`。非公表・請求があれば回答の方針を維持）

## 4B. /features 機能紹介ページ仕様（価値訴求の主戦場）

> トップLPは「30秒で価値が伝わるダイジェスト」、/features は「DL判断を後押しする深掘り」。トップの各機能セクションから該当アンカーへ誘導する。1ページ＋アンカー構成（`#share-image` `#matching` `#trade` `#meguri` `#safety`）。用語は必ず `notes/10` と現行アプリ画面の表記に一致させる（サイトとアプリで呼び名が違うと不信感になる）。

### 4B-1. マイグッズ・ほしいもの・譲求シェア画像（#share-image）

- 訴求：`スマホの中に、自分の譲・求リストがいつでもある`。グッズを登録すれば譲れるもの（マイグッズ）と求めているもの（ほしいもの）が整理され、**譲求シェア画像をすぐ生成**してXへ共有できる
- 表記は「譲・求のシェア画像」。「お品書き」「30秒」は使わない（§4-1確定）。
- 補足：個別の条件（「この2枚セットで」等）も登録できる
- スクショ：SS-2（譲求シェア画像）＋SS-6（登録画面）

### 4B-2. 候補と打診（#matching）

- 訴求：`検索と個別の声かけの往復を減らす`。登録した譲・求の条件が合う相手が候補として並ぶ。気になる相手には提示物・受け取る物・待ち合わせ条件まで含めて**打診**できる
- 補足：打診後は合意前にチャットで条件調整できる（受諾前ネゴ）。`いきなり確定しない・納得してから合意`
- スクショ：SS-3（候補シート）

### 4B-3. 取引チャット — 現地交換／郵送交換（#trade)

- **現地**：合意の前に待ち合わせ場所・時間を確定してから成立。当日は到着状況の共有・任意の現在地共有・服装写真で合流をサポート。`会って直接だから、住所を教える必要がない。送料ゼロ・実物を確認してから交換`
- **郵送**：`住所は取引成立後に、グッズを送る相手にだけ・アプリ内でのみ表示`。外部SNSの個別連絡に住所を残さない。追跡番号の記録で発送状況を確認しやすくする
- （実装メモ：郵送で「匿名」と書かない。高額品には追跡あり配送を推奨する誠実トーン＝`notes/78` §3-3）
- スクショ：SS-4（現地チャット）＋SS-5（郵送）

### 4B-4. めぐり（#meguri）

- 訴求の主語は**「現場がもっと楽しくなる」**（交換の付属ではなく独立した楽しさとして紹介）：
  - **めぐりマップ**：会場や街で、周辺のグルーム・チャットルームが地図に浮かぶ。`いま、この現場に同じ界隈の人がいる`という空気感
  - **グルーム**：写真中心のスナップ投稿。現場の雰囲気・戦利品・デコの共有。閲覧は1km圏内限定
  - **チャットルーム**：現地の情報共有・雑談のスレッド。列状況・物販在庫・落とし物など「現場のいま」をやりとり。無料では同じ都道府県または現在地から約1km圏内で閲覧・参加でき、より広い範囲はMegrumプレミアム（補足に留める・価格や購入導線はGo条件充足後。§0A-1参照）
  - **めぐりあった人**：すれ違った同じ界隈の人が記録され、めぐり広場で振り返れる
- **必須併記**：`正確な現在地は表示されません`＋グルームとチャットルームを分けた閲覧範囲の説明（4-4b と同文）
- （実装メモ：語彙警戒は 4-4b と同じ。「メッセージが送れる」の強調はしない——出会い目的の誤読を招くため、機能列挙の一部に留める）
- スクショ：SS-7＋SS-8＋SS-9

### 4B-5. 安全機能まとめ（#safety）

- 証跡が残る取引・相互評価・通報とブロック・合意前の待ち合わせ確定。`「晒して自衛」から「仕組みで予防」へ`
- → 詳しくは `/safety` へ（重複記述せずリンクで逃がす。文言の二重管理を避ける）

## 4C. /articles 記事基盤・編集仕様

### 4C-1. 目的

- 検索流入だけでなく、アプリ未利用者にも役立つ安全・交換ノウハウを蓄積し、Megrumへの信頼と機能理解につなげる。
- Xやnoteは配信面、megrum.jpは記事の正本と位置づける。全文重複掲載は避け、転載時は要約＋正本リンクまたはcanonical方針を明確にする。

### 4C-2. v1の実装方式

- 記事正本は `web/content/articles/*.md` または `*.mdx` に置き、`web/src/app/articles/page.tsx` と `web/src/app/articles/[slug]/page.tsx` からビルド時に静的生成する。
- Next.js 16対応の具体的なMarkdown/MDXライブラリは、T1着手時に `web/node_modules/next/dist/docs/` の現行ドキュメントを確認して固定する。採用条件はRSC対応、`generateStaticParams`対応、raw HTML無効、依存が少ないこと。
- 記事追加時にアプリコード・DB・CMS管理画面を変更しない。記事ファイルと画像の追加だけで一覧、詳細、関連記事、sitemapが更新される構造にする。
- ブラウザ投稿CMSはv1対象外。Gitを使わない投稿ニーズが継続的に出た時点で別途選定する。

### 4C-3. 必須frontmatter

```yaml
title: "記事タイトル"
description: "検索結果と記事一覧に使う要約"
publishedAt: "2026-07-12"
updatedAt: "2026-07-12"
category: "安全・トラブル対策"
tags: ["グッズ交換", "現地交換"]
author: "Megrum編集部"
reviewedAt: "2026-07-12"
coverImage: "/site-assets/articles/example.webp"
draft: false
relatedFeatures: ["trade", "safety"]
```

- `slug` はファイル名を正とする。`draft: true` は本番一覧・sitemap・静的生成対象から除外する。
- カテゴリは「安全・トラブル対策」「交換ノウハウ」「推し活・現場Tips」「Megrumの使い方」「お知らせ」の5つに限定する。
- 安全、法務、料金、未成年、位置情報、住所に触れる記事は `reviewedAt` を必須とし、`notes/17`・`notes/80`・現行実装との事実確認を行う。

### 4C-4. 記事一覧・詳細

- 一覧：新着順、カテゴリ絞り込み、タイトル、description、公開日、更新日、カテゴリ、カバー画像。「検索窓」は記事数が30本を超えるまで作らない。
- 詳細：パンくず、H1、公開日／更新日、本文、関連記事2〜3件、関連機能リンク、ページ末尾CTA。
- 記事本文へ毎回App Store CTAを割り込ませない。本文読了後と、Megrum機能を直接説明する箇所だけに限定する。
- 記事URLを変更する場合はリダイレクトを用意し、既存被リンクを切らない。

### 4C-5. SEO・構造化データ

- 記事ごとに固有のtitle、description、canonical、OGP、Twitter Cardを生成する。
- `Article` と `BreadcrumbList` のJSON-LDを出す。公開日・更新日・著者・カバー画像はfrontmatterと一致させる。
- `sitemap.ts` に公開記事だけを追加し、`lastModified` は `updatedAt` を使う。記事一覧から孤立するページを作らない。
- キーワードの詰め込みや内容の薄い量産をしない。1記事1検索意図を基本とし、関連記事・`/features`・`/safety`・`/guide/*` を内部リンクでつなぐ。

### 4C-6. 初期公開記事5本

1. `グッズ交換でトラブルを避けるためのチェックリスト`
2. `現地交換で安全な待ち合わせ場所を選ぶポイント`
3. `郵送交換で追跡あり配送を使う理由`
4. `Xで譲・求を探すときに大変になりやすいこと`
5. `Megrumでグッズ交換する流れ`

- 1〜3は安全・法務レビュー対象。4はXを否定せず「探すのはMegrum、告知はX」の共生方針で書く。5は現行アプリ実装の画面名・順序と照合する。

## 5. デザイン要件

- **トーン**：アプリと同一のブランド体験。「かわいいが、ちゃんとしてる」——推し活の楽しさ（lavender/sky/pink の柔らかさ）×安全性の信頼感（余白・整った組版・誇張しない言葉）。
- ブランドカラー：Tailwind テーマの `megrum-lavender / megrum-sky / megrum-pink / megrum-warn / megrum-ok` を使用（HEX直書き禁止・CLAUDE.md 準拠）。

- 既存 `web/src/app/_publicComponents.tsx`（`PublicPage` / `Section` / `TextLink`）を土台に拡張。新規コンポーネントは公開ページ間で再利用できる形で追加。
- スクショの見せ方：iPhone 実機スクショをそのまま角丸+シャドウで。**端末モック枠の自作はしない**（工数と崩れ防止）。
- レスポンシブ：モバイルファースト（流入の大半がXアプリ内ブラウザ想定）。375px幅で完成→デスクトップは余白拡張。
- ダークモード：v1 では対応しない（ライト固定）。
- **実装AIへの指示**：着手時に `frontend-design` スキルで方向性を固め、実装後に `baseline-ui` → `fixing-accessibility` → `web-design-guidelines` → `design-review` のチェーンでセルフレビューすること（オーナー環境 `~/.claude/skills/` 導入済み）。
- ヘッダーは「機能」「安全」「記事」「FAQ」とCTAを主要導線にする。法務・運営者情報はフッターへ置き、モバイルではメニューを開かなくても主要CTAへ到達できるようにする。

## 8. 技術要件

- **実装先**：`web/src/app/`。App Router / RSC。全ページ**静的生成**（SSG）にする（動的データなし・爆速表示）。
- Next.js 16 + React 19 の注意事項は `web/AGENTS.md` を必読（App Router API の破壊的変更）。
- **メタデータ**：静的`metadata`または`generateMetadata`でページ別 title / description / canonical / OGP / Twitter Cardを設定する。OGP画像は静的1枚（ブランドロゴ＋タグライン）から開始。
- **構造化データ**：`SoftwareApplication`（JSON-LD・アプリ名/カテゴリ/OS/価格=無料から）＋ `/faq` に `FAQPage`。
- 記事は§4Cに従い `generateStaticParams` で静的生成し、`Article` / `BreadcrumbList` JSON-LDを付与する。静的metadataで足りるページへ一律に `generateMetadata` を強制しないが、ページ固有のtitle / description / canonical / OGPは必須。
- **パフォーマンス**：Lighthouse mobile 90+ を合格ライン。`next/image` 必須・スクショは priority を1枚だけ・フォントは既存設定を流用。
- **外部アセット禁止**（`notes/63` L100/L108）：公開ページは未説明の外部フォント・外部地図・外部ジオコーディング・外部解析・広告タグを読み込まない。`next/font` は self-host 構成にし `fonts.googleapis.com` / `fonts.gstatic.com` へ出さない。分析（Vercel Analytics等）は Privacy＋外部サービス台帳へ記載してから有効化する（§6-1・§12-3）。
- **アクセシビリティ**：セマンティックHTML・見出し階層・コントラスト AA・キーボード到達性（`fixing-accessibility` スキルでレビュー）。
- `sitemap.ts` / `robots.ts` へ新規ページ追加。`/press` 等未完成ページは sitemap に載せない。
- 公開ページ用の404、記事slug不正時の`notFound()`、draft記事の除外を確認する。
- 通常ユーザー向けWebアプリは作らない。本仕様の公開サイト・記事追加は許可範囲であることを `web/AGENTS.md` に明記して維持する。
- デプロイ：既存 Vercel プロジェクト。プレビューURLでオーナー確認→本番。
